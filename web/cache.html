The attack

Nothing tells a program how big the CPU's caches are. But you can find out by timing, because the memory hierarchy leaks its own shape: reads that hit in L1 take about a nanosecond, reads that go to DRAM take eighty or more. Walk a working set that fits in cache and every access is fast. Grow it past capacity and every access misses. The size at which the timing jumps is the capacity.

That is a side channel — information leaking through a physical property of the machine rather than through any interface designed to provide it. The same measurement, sharpened, is the primitive underneath Spectre, Meltdown, Prime+Probe and Flush+Reload. Here it only recovers your cache sizes, which are harmless. The technique is not.

The original did not work

The 2020 program walked memory with a linear 64-byte stride — one cache line at a time, straight through the window, wrapping at the end. Run it above and the curve is flat: roughly the same nanoseconds per access from 16 KB to 32 MB, across a 2000× range of working-set sizes.

The reason is not a security control. It is the hardware prefetcher. A linear stride is the most predictable access pattern that exists, so the CPU recognises it instantly and streams the next lines into cache before the program asks for them. The misses still happen; their latency never appears, because the data has already arrived. The program was measuring sequential memory bandwidth, which is roughly constant, and its "first 1.5× jump" detector was firing on scheduler noise. Whatever number it printed in 2020 was not derived from the thing it claimed to measure.

The fix is a dependent load chain. Lay the working set out as a single random cycle, where the value at each cache line is the address of the next one. Now load N+1's address is unknown until load N returns, the prefetcher has nothing to predict, and every access pays its true latency. That is the pointer-chase mode, and it produces the real hierarchy.

What about timer coarsening?

The standard browser defence against timing attacks is to blunt the clock. performance.now() is quantised — to 100 µs in Chrome outside a cross-origin-isolated context, and to 1 ms in Firefox and Safari — and SharedArrayBuffer, which can be turned into a high-resolution counting timer, is gated behind Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy headers. The panel on the left shows what this page actually has available; on a double-clicked local file it will report no isolation and no SharedArrayBuffer.

And it does not stop this attack. Coarsening defeats attempts to time a single memory access. This measurement never does that — it times a loop of hundreds of thousands of dependent loads and divides. The timed region lasts milliseconds, so a 100 µs quantum is a rounding error, and even Firefox's 1 ms quantum leaves three orders of magnitude of headroom.

So the live mode runs from a plain file:// page with no server, no headers and no SharedArrayBuffer. That is worth being precise about rather than triumphant: cross-origin isolation is aimed at a sharper class of attack than this one. Recovering cache sizes is coarse and harmless. Recovering a secret byte via Spectre needs to resolve individual accesses, and that is exactly what the mitigation makes hard.

The honest summary is that the defence I expected to be the obstacle was not the obstacle at all, and the thing that actually defeated the original measurement was a performance optimisation nobody put there for security reasons. Working out which of the two was in the way required building it and measuring, not reasoning about it.

Running it natively

The original Java and a smaller C variant are both still in the repository and still run:

Javajavac SideChannelAttack.java && java SideChannelAttack 256 20 1
Ccc -O2 main.c -o main && ./main

Both inherit defect #1 and will produce the same flat result for the same reason. They are kept as the artifact that started this, not as a working tool.

Defects catalogued

  • #1 Linear stride is fully prefetchable — measures bandwidth, not capacity. Fixed via pointer chase; the original is retained as a selectable mode.
  • #2 modu = size - 1 is only a valid mask for powers of two, but the original stepped 1 MB, 2 MB, 3 MB… At 3 MB the mask 0x2FFFFF selects a 2 MB working set. Most windows were not the size they claimed.
  • #3 i * 64 overflows a Java int past i ≈ 33.5 million; with the recommended steps=512 that is 94% of the loop. JavaScript numbers are doubles and do not overflow, so this port is deliberately not bug-compatible here.
  • #4 The detector takes the first 1.5× jump with no repetition and no noise floor, so it reports a boundary even from a flat curve. Replaced; the original is shown alongside for comparison.

What you're looking at

Two cooperating contexts on this one machine — the page and a Web Worker — with no shared variable, no network, no storage between them. The only thing they share is the physical cache. The sender transmits a bit by either hammering a big memory region (a 1) or staying quiet (a 0) during a time slot. The receiver never sees that directly; it just times how long its own memory probe takes. When the sender is hammering, it evicts the receiver's data and the probe slows down. That latency difference is the message.

This is a covert channel between parties who both want to communicate — not an attack that reads a victim's secrets. Both ends are my code, cooperating on purpose. Nothing crosses a trust boundary; there is no victim and no secret. It is a demonstration of a primitive that has been in the security literature for decades (Prime+Probe and its relatives), not a discovery, and there is no vulnerability here to report.

The two hard parts

Timing without a fine clock. The browser's clock is deliberately coarse, but — exactly as with the measurement at the top of this page — that doesn't matter, because each probe times a long loop, not a single access. What does bite is that a probe over evicted memory takes far longer than over resident memory, so a naïve fixed-slot scheme drifts out of sync within a few bits. The fix is Manchester coding: every bit is sent as a transition (a 1-chip and a 0-chip), so the signal carries its own clock and the receiver re-locks on every bit. A short preamble at the start lets it calibrate the fast/slow threshold from the real channel before the message begins.

Honesty about live mode. In the feasibility study the raw contention signal was enormous — a 10× latency swing, idle to saturated — so detecting the sender is easy. Turning that into cleanly-decoded bits live is genuine engineering and depends on the machine and its load. The replay mode is a simulation calibrated to the measured hardware figures, so it always demonstrates the full pipeline; live mode runs the real thing. On the author's hardware the live path decoded a short message intact — 12.5 b/s, 0% bit-error rate, checksum pass, so it is verified to work, not just theorised. Clean decode still depends on the machine and its background load, so it stays labelled best-effort: on a busy laptop it may not land clean bits.

The defence — a dial, not a switch

Here is the part that surprised me, and it corrects a common intuition. You might expect site isolation — putting cross-origin pages in separate processes — to kill this. It doesn't. Site isolation defends against a different thing: one origin's code speculatively reading another's memory inside the same process (Spectre). But the L2 and system-level caches and the memory bus are physically shared across every core and process. Two separate processes still contend for the same silicon, so a contention channel like this one survives process and site isolation.

What actually limits it are measures that degrade the capacity: coarsening the timer, withholding the high-resolution SharedArrayBuffer counter unless a page is cross-origin isolated, and throttling background work. Toggle the timer coarsening or drag the quality slider above and watch the error rate rise and the capacity fall — but never quite to zero without also making the channel useless. That's the real lesson: you can't un-share a cache in software, so the mitigations raise the cost and lower the bandwidth rather than closing the channel outright. Defence in depth, not a padlock.

Reading the readouts

  • Raw bitrate — Manchester halves the data rate, so this is modest by design; a covert channel trades speed for stealth and reliability.
  • Bit error rate — shown, not hidden. With the error-correcting code on, compare the receiver's clean output against the faint “raw decode” beneath the chart.
  • Capacity — the Shannon limit for this error rate and bitrate: the honest information throughput once errors are accounted for. It collapses to zero as the error rate approaches a coin flip.
  • Checksum — a whole-message integrity check, so a corrupted run is reported as corrupted rather than shown as if it were fine.
