The attack

Nothing tells a program how big the CPU's caches are. But you can find out by timing, because the memory hierarchy leaks its own shape: reads that hit in L1 take about a nanosecond, reads that go to DRAM take eighty or more. Walk a working set that fits in cache and every access is fast. Grow it past capacity and every access misses. The size at which the timing jumps is the capacity.

That is a side channel — information leaking through a physical property of the machine rather than through any interface designed to provide it. The same measurement, sharpened, is the primitive underneath Spectre, Meltdown, Prime+Probe and Flush+Reload. Here it only recovers your cache sizes, which are harmless. The technique is not.

Why the obvious version is flat

The obvious way to walk memory is a linear 64-byte stride: one cache line at a time, straight through the window, wrapping at the end. Pick "Naive linear stride" above and the curve is flat, 0.55–0.88 ns per access from 16 KB to 32 MB in the captured run.

Two hardware features hide the misses: the prefetcher, which spots the fixed stride and fetches lines before they're asked for, and memory-level parallelism, because each iteration is independent so the core overlaps many misses at once. This demo doesn't separate the two. The fix defeats both: a dependent load chain, where the working set is one random cycle and each cache line holds the address of the next. Load N+1 can't start until load N returns, there's no pattern to predict, and every access pays its full latency.

Read the boundaries as brackets. The sweep doubles the window each step, so "~128 KB" means the level holds somewhere between 128 and 256 KB of working set. And the "naive first-jump" detector shown beside the table is there as a warning: it reports the window after the jump and has no noise floor.

What about timer coarsening?

Browsers blunt the clock on purpose. performance.now() is rounded to 100 µs in Chrome outside a cross-origin-isolated page, and around 1 ms in some other browsers. SharedArrayBuffer, which can be turned into a much finer counter, needs special Cross-Origin-Opener-Policy / Cross-Origin-Embedder-Policy headers. The panel on the left shows what this page actually has.

It doesn't stop this measurement, but it isn't free. Each sample times hundreds of thousands of dependent loads (milliseconds of work) and divides, so the clock's rounding is a small error. The cost is time: every sample must run long enough to swamp the rounding. That barely matters for measuring cache sizes, but it's what caps the covert channel's bitrate below. Recovering a single secret byte (Spectre-style) requires resolving individual accesses, and that is what coarsening really makes hard.

What you're looking at

Two Web Workers started by this page — a sender and a receiver — pass a message without the payload going through shared memory, the network or storage; the main thread only coordinates. To send a 1, the sender streams through a large buffer for a time slot; for a 0 it waits. The receiver repeatedly times a pointer chase over its own region. When the sender is busy, the receiver's data gets pushed out of the cache they share and its probe slows down. That difference is the message.

It's a covert channel between two parties who both want to talk, not an attack that reads anyone's secrets. Both ends are this page's own code, and the technique has been in the security literature for decades.

Being precise about what this shows

  • Replay is a simulation. It's seeded and calibrated to live measurements (~9 ns idle, ~90 ns busy), so it looks the same on every machine. The badge always says which one you're seeing.
  • Live adapts to your chip. The receiver first measures its own core's cache sizes with a quick sweep (the same pointer chase as the top of this page). Each cache edge suggests a probe size, a ~1 s pre-flight tries each one, and the best is used. That matters because the two ends only have a channel when they share a cache, and which cache that is depends on the chip and on where the OS puts the threads.
  • Live is real, and best-effort. If no probe size reaches 1.6× separation, the page switches to the simulation and says so. On the author's machine the adaptive version reached a live channel in 9 of 11 runs (the previous fixed-size version: 0 of 7). Of the live runs read back from their traces, 2 of 5 decoded cleanly and 3 had one or two flipped bits, each caught by the checksum. Runs started by hand did much better: 8 of 8 landed on the performance cores and decoded the full message intact at 9–11× separation (traces in data/browser/). Save trace keeps all of it, failures included, and records whether the machine was on battery or mains.
  • Timing is agreed out-of-band. The page tells both Workers when to start through an ordinary message, and both sides keep time against the wall clock from that instant. The payload never travels that way, but genuinely isolated parties would have to recover timing from the signal.
  • Manchester coding sends each bit as a transition (occupy→idle or idle→occupy). Here it keeps one calibrated threshold valid for the whole message and makes some errors detectable. Timing comes from the shared start instant, not from clock recovery.
  • Both threads share one process. The argument that such channels survive process, site or VM isolation comes from published research and how the hardware is built. This page doesn't demonstrate it.

Reading the readouts

  • Raw bitrate — 40 ms per chip, two chips per bit. Useful throughput is lower once the preamble, framing and (optional) error correction are counted.
  • Bit error rate — of the decoded message against what was sent. Short messages make this a coarse estimate.
  • Capacity — the Shannon limit, rate × (1 − H(p)), using the raw bit error rate across the whole frame. An upper bound, not something this codec achieves.
  • Save trace — downloads the run as JSON: every latency sample, the threshold, the decoded and sent text, and the settings. It's the same format the native C version writes, so a live result can be kept and checked rather than just reported.
  • Checksum — one byte, sum mod 256. It catches any single flipped message bit, but it's weak against multiple errors.
