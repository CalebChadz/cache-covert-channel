Lab notes: the evidence behind the lesson

The code, the data and the engineering behind each act — what every claim rests on, and what it does not show

The lesson teaches the idea in four acts. These notes are the lab notebook behind it: the code, the measurements, the bugs found along the way, and how strongly the evidence supports each claim. They assume you've been through the lesson, or already know what a cache is. Each section says which act it backs, so you can dip in where you're curious rather than read top to bottom.

The honest framing, up front. Nothing here is an attack on anyone. It measures the computer it runs on, and later has two threads of the same page cooperate on purpose. It leaks no one's data, uses techniques that have been in the textbooks since the 1990s, and is not a vulnerability or a CVE. It is a demonstration of how the physical machine behaves — which is exactly the kind of thing a security analyst should be able to reason about.

1 · Measuring the hierarchy by timing

Backs Act 1 · Measure

Here is the plan, and it is beautifully simple. Take a chunk of memory of some size — call it the working set — and read through it over and over, timing how long the average read takes. Then do it again with a bigger chunk, and bigger, and bigger.

While the whole working set fits inside a cache level, every read is a hit and the average is fast. The moment the working set grows past that level's capacity, the reads start spilling to the next level down and the average jumps. The size at which the timing jumps is the capacity of that cache level. Plot average latency against working-set size and you get a staircase; each step — each "knee" in the curve — marks a boundary in the hierarchy.

There is one trick that makes or breaks this, and it is the pivot of the whole story, so hold the thought: how you walk through the memory matters enormously. The corrected version of the experiment uses a technique called a pointer chase (also: a dependent-load chain). You scatter the working set into a single long loop, where the value stored at each slot is the location of the next slot to visit. To take a step you must read the current slot to find out where to go next.

src/cache/chase.js — laying out the loop

// Lay out a single random cycle over `windowBytes` worth of cache lines,
// so slot perm[0] -> perm[1] -> ... -> perm[n-1] -> back to perm[0].
export function buildChain(buf, windowBytes, seed = 12345) {
  const n = Math.floor(windowBytes / LINE_BYTES);   // one slot per 64-byte line
  const perm = new Int32Array(n);
  for (let i = 0; i < n; i++) perm[i] = i;
  // ... shuffle perm[] into a random order ...
  for (let i = 0; i < n; i++) {
    buf[perm[i] * STRIDE] = perm[(i + 1) % n] * STRIDE;  // each slot stores the NEXT slot's index
  }
  return n;
}

Then the measurement itself is just this loop, timed:

src/cache/chase.js — the timed region

const t0 = performance.now();
for (let i = 0; i < steps; i++) p = buf[p];   // the address of the next read comes FROM the last read
const t1 = performance.now();
return ((t1 - t0) * 1e6) / steps;      // total time / number of hops = nanoseconds per access

That single line, p = buf[p], is the heart of it. Each read depends on the result of the one before, so the CPU cannot run ahead — it must finish read N before it even knows the address of read N+1. Every access therefore pays the true latency of wherever that slot currently lives. (Why that matters so much is §2.) We don't time a single read — the browser's clock is far too coarse for that — we time hundreds of thousands of them and divide, which is why a blunt clock is fine here.

Turning the curve into named boundaries is a separate step, and an easy one to get wrong. My first version used the obvious rule: report a cache size at the first point where latency rises 1.5× — with no repeats, no noise floor, and no check that the curve has any real range at all. The rewrite refuses to guess on a flat curve:

src/cache/detect.js — refusing to invent a boundary

export function detectKnees(points, { minRatio = 1.4, minRange = 3 } = {}) {
  const range = dynamicRange(points);   // slowest reading / fastest reading
  if (range < minRange) {
    // A flat curve has no hierarchy to report. Naming a boundary here
    // would be inventing one — exactly the naive rule's failure.
    return { knees: [], range, confident: false };
  }
  // otherwise: flag every step whose ratio clears minRatio as a knee
}

Two limits are worth stating now, because they bound every result below. First, the sweep doubles the window each step (32 KB, 64 KB, 128 KB…), so a jump between S and 2S only says the level's capacity is somewhere in that range. The page labels it "~S"; read that as "between S and 2S". Second, merging adjacent jumps (to avoid inventing a level out of a gradual roll-off) is a judgement call, and it can also hide a real level. The page shows both the merged and the raw list for that reason.

2 · The plot twist: the obvious version measures the wrong thing

Backs Act 2 · Fail

The obvious way to walk a working set is a linear stride: read byte 0, then 64, then 128, straight through and wrap around. That was my first version, and its inner loop is this:

src/cache/linear.js — the naive linear walk

const modu = windowBytes - 1;
for (let i = 0; i < steps; i++) {
  bytes[(i * 64) & modu] &= 1;   // address = i*64, wrapped to the window: 0, 64, 128, 192, ...
}

Run it and the curve comes out flat. In the captured run shipped with the demo it reads 0.55–0.88 ns per access everywhere from 16 KB to 32 MB: a range of just 1.6× across a 2,000-fold change in working-set size. The pointer chase on the same machine, the same day, spans 79×.

Why is the linear walk flat? Two hardware features hide the miss latency, and this experiment does not separate them:

  • The prefetcher. A fixed 64-byte stride is the most predictable access pattern there is. The CPU spots it and fetches upcoming lines before the program asks for them. (In the kitchen analogy: an assistant who has learned your routine and lines up the next ingredients before you reach for them.)
  • Memory-level parallelism. Every iteration of the linear loop is independent of the last, so an out-of-order core can have many misses in flight at once and overlap their waiting. In the pointer chase, load N+1 can't even start until load N returns, so nothing overlaps.

A cleaner experiment would add the two missing combinations: a dependent chain laid out in linear order (prefetchable, but serialised), and independent loads in random order (unprefetchable, but overlappable). Those aren't in the browser demo, so on its evidence alone the fair statement is "prefetching and/or overlapping hide the latency". The native version runs all four combinations; the answer is in §6 (short version: both do). Note too that the two loops differ in more than access order: one does read-modify-write on bytes, the other plain loads on 32-bit integers.

One more check on the numbers. At 0.55–0.88 ns per 64-byte line, the linear walk is moving roughly 70–115 GB/s, which is more than a single core can plausibly pull from DRAM. So even at 32 MB that walk is mostly served from on-chip caches; the sweep never really tests DRAM. What the comparison does show cleanly is the first edge: between 128 and 256 KB the pointer chase jumps 5×, and the linear walk doesn't move at all.

Update: past 32 MB, and a clock-rounding bug

I later ran the naive walk live up to 64 MB in Safari, whose clock ticks about once a millisecond, and it wasn't flat: 0.25–0.75 ns at small sizes, then 1.0, 1.5 and 2.5 ns at 16, 32 and 64 MB. Two different things were going on.

  • The small-size wobble was clock rounding. Every reading was a multiple of 0.25 ns, because the walk timed a fixed 4 million accesses: 0.25 ns × 4M = 1 ms, exactly one tick. So at the small sizes each sample spanned only 1–3 ticks, and the detector turned a one-tick step (0.25 → 0.50 ns) into a "~64 KB" cache edge. Both live sweeps now grow their step count until each run lasts about 50 clock ticks (at least 10 ms). Each reading records its resolution, the table shows it as ±, and the detector ignores a jump smaller than three ticks. There are regression tests built from that run.
  • The rise past 16 MB is real. Past the on-chip caches the walk has to stream from DRAM, and prefetching can hide latency but not bandwidth. The native stream pattern (plain loads, nanosecond clock, P cores) shows the same shape: a flat 0.77 ns per line from 32 KB to 16 MB, then 0.86–1.15 ns at 32 MB, 0.97–1.36 ns at 64 MB and 1.0–1.27 ns at 128 MB across two runs (data/native/stream-sweep-qos-p.csv). That's 1.3–1.8×, against the pointer chase's ~80×. The browser's rise was bigger (3.3×). One untested guess: its loop does read-modify-write (&= 1), so dirty lines also have to be written back, which roughly doubles the memory traffic.

So the fair statement is: the linear walk is flat across the cache sizes, then rises gently once it reaches main memory. The original capture stopped at 32 MB, which is why it never showed that.

What the naive detector gets wrong. On the shipped linear capture, the first-jump rule happens to report nothing, because no step reaches 1.5×. That is luck, not judgement: it has no way to know the curve is flat, so on a noisier run it would name a "cache size" from jitter. On the pointer-chase capture it reports 256 KB, the window after the jump, which overstates the L1 by 2× and ignores every level beyond it. The lesson I took from it: a confident number is not evidence the measurement worked.

The broader point holds up. What defeated the first version wasn't a security control; it was performance hardware built for unrelated reasons, quietly erasing the signal. You only find that out by running the experiment and asking whether the output could have come out any other way.

3 · The fix: make every load wait for the last one

Backs Act 2 · Fail

The pointer chase from §1 defeats both effects at once. The next address is whatever the current slot holds, and the slots were shuffled into a random cycle, so there's no pattern to prefetch. And because each load needs the previous one's result, nothing can overlap. Every access pays the full latency of wherever its line currently lives.

In the captured run that gives a staircase: about 1.05 ns per access up to 128 KB, a plateau around 5.2–5.5 ns from 256 KB to 2 MB, a gradual rise through 4–16 MB (6.9 → 11.5 ns), then 28 ns at 32 MB and 83 ns at 64 MB.

Aside — doesn't the browser blunt the clock on purpose? Yes. performance.now() is rounded to 100 µs in Chrome outside a cross-origin-isolated page, and around 1 ms in some other browsers (the demo page reports what your browser gives it). That doesn't block this measurement, because it never times a single access: it times a loop lasting milliseconds and divides by the number of loads. What coarsening does cost is speed. Every sample has to be long enough to swamp the clock's rounding, and that is exactly what limits the covert channel's bitrate in §5. Coarsening slows the attack down; it doesn't stop it.

4 · Reality check: does it match the real hardware?

Backs Act 1 · Measure

Provenance. The captured run comes from my own Apple-silicon machine with an A18 Pro chip (6 cores: 2 performance, 4 efficiency), in Chromium, in a non-isolated page. Chrome's user-agent string says "Intel Mac OS X" on Apple silicon; that's a frozen value, not the real CPU. Below, I compare it with the published A18 Pro figures (cited at the end). One thing I can't control from JavaScript is which core the test ran on. The performance and efficiency clusters have different L2 caches, and the operating system can move a thread between them.

The detector on this capture lists four raw jumps (~128 KB, ~8 MB, ~16 MB, ~32 MB) and merges the adjacent ~8 MB and ~16 MB pair into one, giving ~128 KB, ~16 MB, ~32 MB. Read those as brackets, not sizes. "~32 MB" doesn't mean there's a 32 MB cache; it means the working set stopped fitting in any on-chip level somewhere between 32 and 64 MB. That fits a 16 MB L2 plus a ~24 MB system-level cache, but this sweep can't show the two separately.

The gentle rise from 4 MB to 16 MB had two candidate explanations: running out of TLB reach (the address-translation cache covers only a limited span of memory, and a random walk over a large window misses in it), or the thread running on an efficiency core, whose L2 is only 4 MB. The native version tested both (§6). The performance-core run shows the same rise, which rules out the efficiency core. A walk that takes one TLB miss per page instead of one per access stays flat right up to 16 MB, which points to translation cost.

I also ran a finer sweep with windows between the powers of two, which narrowed the L1 edge to 128–192 KB and showed an intermediate ~19 ns step at 24 MB, where a system-level cache would sit. That sweep's code and data aren't in this repository, so I'm not relying on it for anything above. Its absolute latencies also ran about 50% higher (around 1.5 ns at L1). Run-to-run absolute numbers vary; the shape is what reproduces.

5 · The finale: turning the clock into a covert channel

Backs Acts 3 & 4 · Talk and Defend

So far the timing trick only reads a harmless fact about the hardware. The finale puts it to work. Two Web Workers started by the same page, a sender and a receiver, pass a message using contention for a shared cache, not any channel built for communication. (Earlier versions put the receiver on the page's main thread; why that changed is below, under "Adapting to the chip".)

To send a 1, the sender streams through a large buffer as hard as it can for one time slot; to send a 0 it waits. The receiver repeatedly times a pointer chase over its own region. When the sender is busy, the receiver's probe slows down. (The figures below come from the original fixed sizes, a 24 MB sender buffer and an 8 MB probe; the current version sizes both from a measurement of the chip.)

src/cache/channel.js — the sender, running in a Worker

// A '1' chip: saturate the memory subsystem continuously for ~a few ms.
function thrash(ms){
  const step = 64; let acc = 0; const t0 = performance.now();
  while (performance.now() - t0 < ms){
    for (let i=0;i<buf.length;i+=step) acc ^= buf[i];  // stream a big region, over and over
  }
  return acc;
}

src/cache/channel.js — the receiver's probe, running in a Worker (a dependent-load chain, as before)

function walk(steps) {
  const t0 = performance.now();
  for (let i = 0; i < steps; i++) p = pool[p];  // same pointer chase — its speed reveals whether we were evicted
  return ((performance.now() - t0) * 1e6) / steps;
}

The live numbers line up with the hardware story. In the measurements the simulator is calibrated from, the receiver's probe read 8.7 ns with the sender idle and 90.3 ns with it busy, a ~10× swing. 8.7 ns is close to the captured sweep's 7.8 ns at 8 MB (the region sitting in cache), and 90 ns is close to its 83 ns DRAM figure (the region pushed out to main memory). So the likeliest mechanism is eviction: the sender's 24 MB stream pushes the receiver's 8 MB out of the shared cache. The browser can't separate that from memory-bandwidth contention; the native cross-cluster test in §6 can, and it supports eviction.

src/cache/channel-sim.js — the model, straight from the measured hardware

export const MODEL = {
  idleNs: 9,   // receiver probe when the sender is quiet (region still resident)
  busyNs: 90,  // receiver probe when the sender saturates the cache/bus
};

What is and isn't shared

  • The payload never travels through a normal channel to the receiver. The decoder's only input is the list of latency samples.
  • The start time does. The page gives both Workers a start instant (and the sender its chips) via postMessage, and both sides schedule every chip from that instant on the wall clock. Handing the sender the message is fine (a sender has to know what it's sending), but agreeing on the clock out-of-band is a convenience. Two genuinely isolated parties would have to recover timing from the signal itself, and this demo doesn't attempt that.
  • Both threads live in one browser process, on the same origin. That makes this the easiest possible setting for the channel, not the hardest.

Why the signal is easy but the message is hard

Detecting that the sender is busy is easy. Turning that into reliable bits is the hard part, and most of the difficulty is synchronisation. My first attempts used fixed time slots and decoded at a bit-error rate around 0.5 (a coin flip), even though the raw samples showed a clear 6–9× separation. The cause: the receiver's probe takes about ten times longer when its data has been evicted, so a receiver that starts each slot "when the last probe finishes" runs late on every 1 and drifts out of step within a few bits.

What the live code actually does about it:

  • Absolute chip boundaries. Both ends compute every chip's start and end from the one shared start instant, so a slow probe can't push later chips out of place, and errors don't build up.
  • Guard windows and medians. The receiver only samples between 25% and 90% of each 40 ms chip, which avoids the moments when the sender is ramping up or winding down. It takes the median of several fixed-size probes, which shrugs off one-off interruptions.
  • Manchester coding. Each bit is sent as a transition: a 1 is occupy-then-idle, a 0 is idle-then-occupy.

src/cache/manchester.js — every bit carries its own clock edge

export const CHIPS_FOR_1 = [1, 0];   // data 1 → occupy, then idle
export const CHIPS_FOR_0 = [0, 1];   // data 0 → idle, then occupy

export function manchesterEncode(bits) {
  const chips = [];
  for (const b of bits) chips.push(...(b ? CHIPS_FOR_1 : CHIPS_FOR_0));
  return chips;
}

Manchester coding is often described as "self-clocking", and in principle it is: the guaranteed edge in every bit lets a receiver recover timing. This decoder doesn't do that. It pairs up chips at fixed positions, because timing already comes from the shared start instant. What Manchester buys here is balance and error detection. Every bit is exactly one slow chip and one fast chip, so a single threshold, calibrated once from a 32-chip preamble, stays valid for the whole message. And a 00 or 11 pair can't be a valid bit, so it's flagged as a violation.

A frame is: preamble, then a start-of-frame byte, a length byte, the message, and a one-byte checksum (sum mod 256). There's an optional repetition-3 error-correcting code (each bit sent three times, majority vote), and the page shows the raw and corrected decodes side by side. The codec is pure and deterministic, and it's unit-tested against simulated traces with known noise, so its logic is checked without real hardware in the loop. The live path, by contrast, has no automated tests.

The live result, stated precisely

On my machine the live channel decoded the message cache intact, with the error-correcting code off: all 40 message bits correct and the checksum passing. A few individual chips did flip (visible as red dots early in the latency plot), but the bit decisions still came out right. Here is what that does and doesn't show:

  • Speed. The raw rate is 12.5 bits/s: 40 ms chips, two chips per bit. The useful rate is lower, because the frame adds a 32-chip preamble plus start, length and checksum bytes. Sending cache takes 160 chips (6.4 s) for 40 bits of message, about 6 bits/s, before the ~1 s pre-flight check. With the error-correcting code on, it's about 2.4 bits/s.
  • Error rate. "0 errors in 40 bits" is a small sample. It rules out a high error rate, but a true rate as high as ~7% would produce a clean 40-bit run fairly often (the rule of three gives 3/40 as a rough 95% upper bound).
  • Reproducibility. The raw samples from that run aren't in the repository, so it's a reported observation, not data you can inspect. The demo now has Save trace, so any run can be kept as data. If no probe size separates well enough in the pre-flights, the page switches to the simulation and labels the result SIMULATED rather than presenting noise as a decode.

Adapting to the chip (and why it used to fail)

After the site moved to GitHub Pages, live mode stopped finding a channel at all. The code hadn't changed, so I logged what the receiver measured. It read 8.3 ns per access until the sender started (the performance cores' L2 figure for an 8 MB region), then 140–370 ns on every chip, 1 or 0. Those are efficiency-core numbers: that cluster's L2 is only 4 MB, so an 8 MB probe falls out to main memory there. macOS had moved the page's main thread to the other cluster once the sender got busy. §6 shows that a split across clusters means no channel, so the earlier successes depended on how the OS happened to place the threads.

The live path now does three things differently:

  • Both ends are Workers. They get equal priority, so the OS tends to place them together. The main thread only coordinates, which also keeps the page responsive.
  • It measures before it transmits. The receiver runs a quick sweep (~1 s) on whatever core it landed on. The knee detector from §1 finds that core's cache edges, and each edge proposes a probe that fills 85% of that level, plus one roomier probe. A ~1 s pre-flight tries each candidate on the same pair of Workers, and the best is used. The sender's buffer is sized to overflow the largest level found. So a 4 MB efficiency-core L2, a 16 MB performance-core L2 or a 32 MB desktop L3 each get a probe that fits.
  • Bits are decided by comparing the two halves of each Manchester bit, not by testing each half against one threshold. Native testing showed this survives the latency level drifting mid-message.

I compared the two versions in alternating runs on the same machine and afternoon. The old version reached a live channel in 0 of 7 runs (pre-flight separation 0.5–1.2×). The adaptive one reached it in 9 of 11. In practice it found the workers on the efficiency cores, and the 2.4–3.4 MB probes won with 2.3–3.4× separation. Of the six runs I read back from their saved traces, five reached a live channel: 2 decoded cleanly and 3 had one or two flipped bits (cAche, cac(, aáche), each rejected by the checksum. The sixth fell back to the simulation. So the channel is now usually there, but at 40 ms chips it is still too noisy to be reliable. Longer chips or error correction would be the next things to try. Caveats: one machine, one session, and a browser driven by automation tooling, which may itself affect scheduling.

That last caveat turned out to matter. Live runs started by hand (eight so far, traces in data/browser/) look completely different. Their calibration put the receiver on the performance cores: ~6 ns per access flat to about 8 MB, edges at 16 and 32 MB. The adaptive choice was a 4.8 or 6.8 MB probe, the pre-flights separated 9–11×, and all eight decoded the full message intact, seven on the first attempt, including the 16-character cache me outside. The samples alternate ~92 / ~9 ns, the same contrast the native measurements and the original calibration show. So the automated tally above probably understates a real visitor's experience. Driven by automation, the Workers kept landing on the efficiency cores; started by a person, they landed on the performance cores. Eight runs on one machine is a strong pattern, not a general result. Note that the adaptive design picked a sensible probe in both cases (~3 MB on the efficiency cores, ~5–10 MB on the performance cores).

Those traces also exposed a calibration bug. A few sweep points read 0 ns: the step count had been scaled from a pilot too short for the 100 µs clock to tick, and the lower of two readings was kept. The zeros created fake cache edges, which cost a wasted pre-flight (a 1.2 MB probe, 1.0×). The sweep now grows its step count until each measurement spans many clock ticks, and the planner ignores unusable readings. There's a regression test built from that trace.

Every trace now records the power state as well (Chromium's battery API in the browser; pmset or sysfs natively). Every successful live run so far happened on battery, so "does mains power change core placement?" is now testable rather than a guess. Runs so far are listed in data/power/.

A one-bit ghost: "cacHe". On a different live run the message came back as cacHe. Lowercase h is 0x68 = 0110 1000; uppercase H is 0x48 = 0100 1000. They differ by exactly one bit, the ASCII case bit. One bit flipped by noise changed one letter and nothing else, which is a good picture of why the frame carries a checksum: a sum-mod-256 checksum catches any single flipped message bit, and the repetition code would correct it. (An 8-bit sum is weak in general, though; some combinations of two flips cancel out and slip through.)

Defences — what this demo does and doesn't show

A common intuition is that site isolation (browsers putting different sites in different processes) should close a channel like this. It probably doesn't, but be clear about where that conclusion comes from. Site isolation targets Spectre-style attacks that read another site's memory inside the same process. A contention channel doesn't read anyone's memory. It works because the last-level cache and memory system are physically shared across cores and processes. Research has shown cache covert channels between separate virtual machines in the cloud (Maurice et al., NDSS 2017, ran SSH over one), and OpenAI's October 2026 red-team report described agents in separate microVMs signalling through a CPU cache. This demo doesn't test any of that. Both its threads are in one process, so it illustrates the mechanism, not the cross-process claim.

The defence dial in the lesson (Act 4) is a simulation. The quality slider adds random noise and shrinks the gap between slow and fast in the model. The "coarsen the receiver's timer" checkbox rounds the simulated latencies to a 25 ns grid, a value chosen to visibly blur the two levels, not one derived from any real browser setting. It's a fair illustration of how errors eat into capacity. It is not a measurement of any real mitigation. In fact, as §3 explains, real timer coarsening mostly doesn't raise the error rate. It forces longer probes per sample, which lowers the bitrate.

The capacity readout is the Shannon limit for a channel that flips bits at random: rate × (1 − H(p)), where p is the raw (before error correction) bit error rate measured across the whole frame. It's an upper bound on useful throughput at that error rate, not something this codec achieves.

The realistic bottom line: you can't un-share a cache in software. What mitigations really do is make channels like this slower and noisier (coarser timers, no high-resolution SharedArrayBuffer counter without cross-origin isolation, throttled background threads) or remove the sharing in hardware (partitioned caches, separate physical machines).

6 · The native version: testing what the browser couldn't

Backs Acts 1–3, beyond the browser

Several questions above ended in "this demo can't tell". The C programs in native/ exist to answer them. They have a nanosecond clock, windows at four sizes per doubling, and a scheduler hint that steers a thread to the performance cores (P) or the efficiency cores (E). All results below are from the same A18 Pro machine, and the raw CSV and JSON files are in data/native/.

The P-core L1 latency, 0.78 ns, is about 3 cycles at 4.04 GHz, which matches the ~3-cycle load-to-use latency measured for Apple's performance cores (7-CPU, cited below). The browser's 1.05 ns is about one cycle of JavaScript overhead on top. The E-core run is noisy (background priority gets interrupted a lot), but both of its edges land on the sizes macOS itself reports for this chip (sysctl hw.perflevel1: 64 KB L1d, 4 MB L2). Both effects are real, and each one alone is enough to hide most of the latency. Overlapping independent loads (scatter) hides about 90% of it even with no pattern to predict. More surprising, a dependent chain in sequential order (chain) costs about 1 ns per access even out to 128 MB. Each load waits for the previous one, and yet the latency still disappears. That fits Apple's load address predictor, which guesses where a load will go before its address is known (Kim et al., SLAP, 2025), though an aggressive prefetcher would look the same from here. The practical upshot for §2: on this chip, "make the loads dependent" is not enough. The addresses must be unpredictable as well.

The 4–16 MB rise is address translation

A pagechase mode visits pages in random order but finishes every line in a page (also in random order) before moving on. That keeps the walk unpredictable but takes one TLB miss per 16 KB page instead of roughly one per access. On the P cores the ordinary chase climbs from 5.4 ns at 2 MB to 11.3 ns at 16 MB; pagechase stays at 4.8–5.2 ns across that whole range. So that rise is translation cost, not a cache running out. (Past 16 MB the control stops being clean, because finishing a page at a time hands the hardware spatial locality, so I don't use it there.)

The channel between two separate processes

native/channel removes the browser demo's two shortcuts. The sender and receiver are separate processes with no shared memory, pipe or file. And there's no shared start time: the sender waits a random 200–700 ms that only it knows, and the receiver has to find the frame on its own. It sets a threshold from the data alone (Otsu's method), finds the start by matching the preamble at every possible offset, and uses the start-of-frame byte to settle the one-period ambiguity in an alternating preamble. It decodes each bit by comparing its two halves directly. It uses 20 ms chips (10 ms failed every time); the receiver samples every 1 ms.

Each configuration was run 20 times:

What that shows, and what it doesn't:

  • The channel works between separate processes with no agreed start time: 39 of 40 clean decodes on default scheduling. This is the claim the browser demo could only argue. It's processes on one machine, not VMs, so the VM claim still rests on published work.
  • It works by eviction from a shared L2. With the sender on the E cores and the receiver's 8 MB region in the P cores' separate L2, there is no channel at all, even though the sender is still streaming 24 MB through shared main memory. When the receiver probes 64 MB instead (too big for L2, so its probe goes out to shared memory too), a weaker channel appears. That's bandwidth or system-level-cache contention, and it's real, but much less reliable.
  • Steering both ends to the P cores made it worse (7/20). I don't know why. One guess is that the scheduler then puts both on the same core, or that higher priority invites more interruption, but I haven't tested either.
  • The checksum never passed on wrong text in these 100 runs. That wasn't true of my first decoder: its self-test found that letting the checksum choose between candidate offsets made a wrong-but-passing result about 10% likely under heavy noise. The decoder now ranks by preamble match and uses the checksum only to verify. With an 8-bit checksum, a false pass remains possible in principle.
  • Speed. 20 ms chips give 25 bits/s raw, and about 12 bits/s of message once the frame overhead is counted. That's twice the browser version, and well below what a tuned channel could do. I haven't tried to optimise it.

The cacHe ghost from §5 turned up again in the P-core batch: the same single case bit, flipped by noise, and caught by the checksum.

7 · Replicate it yourself

Everything in the demo is in this repository. There's no framework and no install step for the pages, and each page is a single self-contained file.

What's in the repo

  • src/cache/chase.js — the pointer-chase measurement.
  • src/cache/linear.js — the naive linear-stride walk, kept so you can watch it come out flat.
  • src/cache/detect.js — turns a curve into bracketed boundaries, and refuses to when there's no real range.
  • src/cache/manchester.js — the codec: text → bytes → bits → chips and back, with preamble, framing, checksum and optional error correction.
  • src/cache/channel.js — the live channel: sender and receiver Workers, the calibration sweep, planFromCalibration (cache edges → probe sizes) and the pre-flights.
  • src/cache/channel-sim.js — the seeded simulator behind replay mode, the defence dial and the tests.
  • data/cache/fixtures.json — the captured sweeps plotted in §2 and in the lesson.
  • native/ — the C measurement (chase.c), the cross-process channel (channel.c) and batch.sh; data/native/ holds their results.
  • test/ — unit tests for the codec, simulator, detector and window maths; make -C native test runs the C decoder's self-test on synthetic traces. The live paths themselves are not unit-tested.

How to run it

You need Node.js (v18 or newer) only to build the pages and run the tests; the built pages themselves need nothing. From the repository root: 

npm test         # unit tests (codec, framing, simulator, detector)
npm run build    # rebuild the self-contained pages into dist/
make -C native   # build the C tools (any C11 compiler)
./native/channel run hello --trace out.json   # two processes, in-band sync

Then open dist/index.html in a browser (double-click it; no server needed). Choose "Pointer chase — live on this machine" and press Run to measure your hierarchy, then switch to "Naive linear stride — live" to watch the same clock report a flat line. Scroll to the finale to send a message through the cache.

Experiments worth trying — including ones that could prove me wrong

  • Check §6 on your machine. Run ./native/batch.sh 20 and compare the rates. Different chips have different cache layouts, and the cross-cluster result especially may not hold elsewhere.
  • Go further than processes. Run the sender and receiver in two VMs, or two containers on one host. That's the step from this repo's evidence to the cross-VM claim.
  • Save a live browser trace. Run the browser channel in Live mode and press Save trace. The JSON has every sample, so a reader can check the decode instead of trusting the screenshot.
  • Measure real coarsening. Serve the page with cross-origin isolation headers (finer clock) and without, then compare live error rates at a fixed chip length. §3 predicts little difference in errors, only in the shortest usable chip length.

Where to go deeper

These are the reputable, mostly beginner-approachable sources behind the concepts here, if you want to keep pulling the thread:

  • Caches and the memory-speed gap: Ulrich Drepper, What Every Programmer Should Know About Memory (2007) — the canonical deep-dive on why caches exist and how they behave. akkadia.org/drepper/cpumemory.pdf. A gentler start is Wikipedia's CPU cache article.
  • Prefetching (the §2 villain): Wikipedia, Cache prefetching, plus the prefetching sections of Drepper above.
  • The A18 Pro hardware figures (the §4 published specs): The Apple Wiki — A18 Pro for cache sizes (L1d 128 KB per performance core, 16 MB L2 shared by the performance cores; the ~24 MB system-level cache is flagged uncertain) and clock. Apple P-core L1 load-to-use latency is documented for the closely related Firestorm core at 7-CPU — Apple M1 (3–4 cycles). General background: Wikipedia — Apple A18.
  • Cache timing as an attack primitive: Colin Percival, Cache Missing for Fun and Profit (2005) — very readable, and the paper that popularised cache covert channels between threads. daemonology.net/papers/htt.pdf. The classic Prime+Probe treatment is Osvik, Shamir & Tromer, Cache Attacks and Countermeasures: the Case of AES (2006), eprint.iacr.org/2005/271.
  • Cache covert channels between virtual machines: Maurice et al., Hello from the Other Side: SSH over Robust Cache Covert Channels in the Cloud (NDSS 2017).
  • The 2026 red-team report: OpenAI, Securing our frontier model training environment (23 Oct 2026), section "Communicating across isolated tasks". Agents were given attack objectives, and in most of these tests were directed to a specific channel or given an encoding protocol.
  • Apple's load address predictor: Kim, Genkin et al., SLAP: Data Speculation Attacks via Load Address Prediction on Apple Silicon (2025). Relevant to why the sequential dependent chain in §6 hides latency.
  • Cache attacks in the browser (closest to this demo): Oren et al., The Spy in the Sandbox — Practical Cache Attacks in JavaScript (2015), arxiv.org/abs/1502.07373.
  • Spectre (why the timer defences exist): Kocher et al., Spectre Attacks (2019), spectreattack.com/spectre.pdf.
  • Covert & side channels, background: Wikipedia, Covert channel and Side-channel attack.
  • The browser's timing defences: MDN on performance.now() and SharedArrayBuffer (and the COOP/COEP isolation it needs).

One more time, because it matters: this is cooperative and educational. It leaks no one's data, it measures only the machine it runs on and sends nothing anywhere, the techniques are decades old and documented above, and there is no vulnerability here to report. The point was never to break something — it was to understand what the machine is really doing, closely enough to tell the difference between what a program claims to measure and what it actually measures. That difference is where the interesting security questions live.
